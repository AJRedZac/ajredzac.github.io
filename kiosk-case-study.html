Self-Service Ticketing Kiosk

Java 21 · JavaFX · Spring Boot · native SDK integration · Windows printing

Primary developer · 2026

The problem

Travelers at intercity bus terminals queue to buy tickets from an agent. The kiosk removes the queue — but to do that, an unattended machine has to take card payments, print a ticket the traveler can board with, and stay correct when a passenger walks away mid-purchase. There is no operator to recover from a bad state. Whatever the software does when something fails is the final answer.

Constraints

  • No operator at the machine. Every failure path has to end somewhere a traveler can act on without help.
  • The payment terminal is driven by a closed vendor SDK: a proprietary JAR that loads a native Windows DLL internally. Its internals are not inspectable and it cannot be run in CI.
  • Money is captured on the device; the record of the sale lives in a cloud backend. There is no transaction spanning both.
  • Prices, fare rules and printed footer restrictions are decided by the backend, not the kiosk.

What I built

  • A four-layer desktop application in Java 21 and JavaFX, running on Spring Boot with the HTTP server disabled — the framework was there for dependency injection and its HTTP client, not to serve requests.
  • A multi-modality sales engine: reserved-seat, open-date, round-trip, and mixed trips that combine a reserved leg with an open one.
  • Two hardware integrations. Card payments go through a proprietary vendor JAR that loads a native Windows DLL internally. Thermal printing goes through the Windows print service, with printer status read separately from the vendor's native status API bound with JNA — reading real device state before committing to a print, rather than discovering a fault halfway through a ticket.
  • A thermal document renderer: five document types — reserved-seat, open and express tickets, payment voucher, travel-insurance receipt — sharing a common typographic skeleton, with the tax breakdown and footer restrictions driven entirely by backend data.
  • Event-driven peripheral telemetry reporting device health, system metrics and network latency, with thresholds configurable through application properties and environment configuration.
  • Session and inactivity management with two independent timers that cancel backend reservations when a traveler abandons the flow.

Three decisions worth explaining

1. A timeout that stops waiting is not a timeout that stops work

The kiosk would occasionally freeze during a card payment. The PIN pad is driven by a vendor JAR that loads a native Windows DLL internally, and in certain device states the native call simply never returned.

The obvious fix — wrapping the call in a future and calling get with a timeout — does not work, and understanding why is the whole lesson. Java's interruption is cooperative: it sets a flag that Java code checks. A thread parked inside a native library checks nothing. Neither a timeout nor a cancel brings it back. All you have achieved is that you stopped waiting. The thread is still in there, still holding whatever it acquired.

That distinction matters because of what comes next: if you retry after such a timeout, a second call enters the SDK while the first is still inside. That is no longer a frozen screen — it is a poisoned transaction, with real money involved.

The fix had three parts. A single dedicated thread for every native call, so serialization was structural rather than a convention someone had to remember. A busy flag set by the native callable itself — raised on entry, cleared in a finally only after the native call actually returns — rather than inferred from the future's state, because the future's state is exactly the thing that lies. And an atomic guard, so two callers arriving at the same instant could not both pass the check and enqueue.

The watchdog was then reframed honestly: not recovery, but containment. There is no in-process recovery from a hung native call. The watchdog frees the UI and blocks further work against an SDK we know is compromised — and deliberately does not try to tidy up after it, because reaching back into a library that is still executing is just a second collision with extra steps.

2. A card charge has no rollback, so the compensation has to be explicit

There is no distributed transaction available between a physical payment terminal and a cloud backend. The money is captured by the device; the record of the sale lives in the backend. The delivered flow prices the trip first, then runs a single direct sale on the device, then confirms that sale in the backend. There is no pre-authorisation hold and no separate commit step: when the device approves, the charge has happened.

So payment crossed two boundaries that fail independently: a proprietary native device, and a remote system of record. What that buys is simplicity. What it costs is that the two can disagree, and the useful question stops being what the happy path looks like.

Some boundaries are easy. A declined card needs no compensation, because nothing was captured. When the device reports a timeout and a reliable transaction reference exists, compensation is attempted on a best-effort basis.

A hung native call is treated differently. Because the Java process cannot establish the final device state or obtain a reliable transaction reference, it has no basis for a safe in-process compensation — and not knowing the outcome is not the same as knowing there was none. So the application contains the call, blocks concurrent attempts so the ambiguity cannot be compounded by a duplicate, and leaves the ambiguous outcome to be resolved against authoritative state rather than guessed at locally.

Printing happens after the sale is confirmed, so a printer failure does not roll back the sale. The confirmed transaction is preserved, and delivery falls back to a channel that is actually available: a digital copy if one was already sent, otherwise the UI shows the purchase reference number and directs the traveler to assisted service.

That is the part worth taking away, and it generalises well beyond kiosks. When a remote system of record cannot confirm its own state, an automatic reversal is a guess with money attached. Blind compensation is not safety — it is a second uncertain write on top of the first. So the application avoided guessing: it contained the local operation, prevented duplicate attempts, and deferred compensation until an authoritative state could be established. I also documented a reconciliation design for a later hardening phase.

Writing the payment as an ordered protocol instead of scattered error handling is what made those boundaries legible in the first place — including the ones that were deliberately left un-automated.

3. Hardware you cannot test is hardware you cannot trust

Hardware boundaries were isolated behind interfaces expressed in domain terms — nothing from the vendor SDK leaks through them — with production adapters and test doubles for the integrations that required them, selected by Spring profile.

The most useful double is the least obvious one: an explicit unavailable implementation that fails loudly. A silent mock in development lets you believe a flow works when you have never touched the device. The unavailable one tells you that you are running without hardware, instead of letting you find out at the terminal on demo day.

The scenario doubles are where the real value is. They let you write the test for what happens if the payment device stops responding at the exact moment the charge is in flight — a case you cannot reproduce with real hardware no matter how hard you try. They are also the only reason the hung-call behaviour in Figure 1 has tests at all: the vendor JAR cannot run in CI, so the boundary is the thing under test.

Engineering practice

The project ran on spec-driven development: features were specified in technology-agnostic documents with an explicit open-questions section, so ambiguity became an artifact someone had to resolve rather than an assumption buried in code. I wrote 26 architecture decision records. Static analysis was wired into the build — a SonarQube project configuration with justified rule suppressions lives in the POM — and dependency-scanning findings drove a framework upgrade that closed a set of transitive CVEs. Security work included encrypting the payment SDK credentials at rest with Windows DPAPI under current-user scope, stripping CR/LF out of logged request data to close a log-forging finding, and masking personal data in integration logs.
